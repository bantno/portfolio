## Problem & Approach

Built an autonomous maze solver for a TurtleBot3 (ROS2) that navigates by reacting to directional signs posted at each decision point. The robot is driven by a single state-machine node that interleaves three sensing modalities — LIDAR for proximity, the camera for sign reading, and odometry for heading — into a simple, reliable loop:

- **Drive** forward on `/cmd_vel` until the LIDAR's forward segment averages under 0.6 m, indicating a wall (and therefore a sign) ahead.
- **Read the sign.** The camera frame is segmented with an HSV color threshold, the largest qualifying contour is extracted as the sign region, cropped, and resized to a 33×25 binary patch. A KNN classifier (k=3, trained on ~130 labeled images) maps that patch to one of five maneuvers: turn left, turn right, U-turn, stop, or goal reached.
- **Turn** to the new heading using an odometry-based proportional controller (dead reckoning), then resume driving.

I started with the ROS2 Nav2 stack but iterated away from it to this lightweight dead-reckoning approach, which proved far more repeatable in the constrained maze than full path planning.

The system was developed in Gazebo — which required adding a simulated Raspberry Pi camera to the TurtleBot3 Burger model (custom SDF/URDF) — and then run on real hardware. The perception and control logic is shared across both; a single flag swaps the camera interface (Gazebo's raw `Image` on `/camera/image_raw` for a Raspberry Pi `CompressedImage` published with best-effort QoS to survive the WiFi link). Keeping the classifier and heading control identical across environments is what let the sim-tuned pipeline hold up against real-world lighting and sensor noise.
